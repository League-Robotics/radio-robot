## 2026-08-04 update (132-019): the 11.1-point L/R gap, closed

Sprint 132's headline hardware ticket. The 11.1-point L/R plateau-tracking
gap found by the 2026-08-03 motor survey (`tovez`: L 96.0% / R 84.9%,
`output/motor_survey_20260803/README.md`) is a per-wheel Stage-A
(`App::Drive::corrGain_`) deficiency, not a population-scale
`duty_per_speed` problem (that field is already correct, per 132-009).
Corrected with a gain-only per-wheel affine correction pushed through
132's new config wire (`SetConfigField`, `ConfigTarget::DRIVE`), then
baked into [`data/robots/tovez.json`](../../../../data/robots/tovez.json)
(`drive._wheel_correction_132_019_note` has the full derivation) and
reflashed. Full run-by-run numbers, in order, with boot state, are in
ticket `132-019`'s own completion notes
(`clasi/sprints/132-.../tickets/done/019-....md`); summary:

| stage | trapezoid L / R plateau | gap | square L / R plateau | gap |
|---|---:|---:|---:|---:|
| baseline, this session, run1 (cold) | 83.1% / 70.8% | 12.3 | 82.2% / 76.0% | 6.2 |
| baseline, this session, run5 (warm, most converged) | 91.7% / 80.7% | 11.0 | 89.8% / 79.3% | 10.5 |
| **cold boot, POST reflash+bake** | **97.5% / 101.9%** | **4.4** | **101.3% / 97.2%** | 4.1 |
| warm, post reflash+bake | 99.6% / 102.0% | 2.4 | 103.2% / 97.2% | 6.0 |

Both wheels now land close to (occasionally a few points over) 100% —
not further tuned, since a same-connection live-push demonstration
(`019_sameboot_A_preop` -> `019_sameboot_B_postpush` below) already showed
some overshoot and this ticket's own instruction is to report the
measured result, not iterate until it looks perfect.

**Methodology finding, worth keeping visible**: `SerialConnection.connect()`
over direct USB pulses DTR on every open, which resets `tovez`'s
microcontroller (`serial_conn.py`'s own doc comment). A live
`SetConfigField` push to `DRIVE` is RAM-only (`DRIVE` is not in
`Configurator::persistIfEligible()`'s flash-persistence table) and is
silently wiped by the very next reconnect — even with no power cycle.
Verifying a live push therefore requires measuring in the SAME connection
as the push (see `019_sameboot_*`); two separate `velocity_profile_gate.py`
invocations will silently discard the push before the second one starts.
This is also why only the BAKED path (this file's own `drive.*` fields)
satisfies "survives a cold boot" — a live `DRIVE` push structurally cannot.

Artifacts: `019_run1_coldboot_pre` .. `019_run5_warm4_pre` (baseline, this
session, uncorrected, 5 back-to-back runs), `019_run6_warm_postpush1`
(a discarded methodology step — this run's own connect() silently reverted
the live push before it started; kept for transparency, not as evidence),
`019_sameboot_A_preop` / `019_sameboot_B_postpush` (the valid live-push
demonstration, one connection, no reconnect), `019_run7_coldboot_post1` /
`019_run8_warm_post1` (post-reflash, baked correction, the real acceptance
numbers), `019_summary.csv` (all of the above, one row per profile per
wheel per run).

Both profiles: 3.0 s window, 450 mm commanded, identical area — only the shape

## Headline: the robot drives short after a power cycle, and converges

**Distance fidelity is not a fixed property of this robot — it depends on how
much the robot has already driven since boot.** From a cold power-on it
delivers ~83% of commanded distance; after three back-to-back 3-second runs
(~10 s of driving, no reflash, no config change, nothing touched) it reaches
~96–98%. Both wheels do this, together.

### Same boot, three consecutive runs, nothing changed between them

Plateau speed reached, as a fraction of commanded (the cleanest convergence
signal — it is measured mid-profile, away from the ends):

| run | trapezoid L | trapezoid R | square L | square R |
|---|---:|---:|---:|---:|
| 1 (cold) | 79.6% | 81.6% | 85.0% | 83.1% |
| 2 | 87.4% | 84.5% | 87.9% | 86.8% |
| 3 | 91.7% | 86.4% | 95.5% | 89.7% |

Delivered distance ÷ commanded:

| run | trapezoid L | trapezoid R | square L | square R |
|---|---:|---:|---:|---:|
| 1 (cold) | 82.4% | 82.9% | 85.1% | 84.2% |
| 2 | 92.0% | *(not captured)* | 88.9% | *(not captured)* |
| 3 | **98.0%** | 93.1% | **96.2%** | 93.1% |

Monotonic on every wheel and both profiles. The distance shortfall is the
integral of a velocity the loop has not yet learned to reach — the plateau
tracking and the delivered ratio move together.

This is consistent with an adaptive/bias term in `App::Drive`'s wheel-speed
controller that starts from zero at boot and converges over repeated motion.
That is a hypothesis from the numbers, not a code reading — it has not been
confirmed against the firmware.

**Why it matters:** a robot that does its first competition run straight after
power-on drives ~17% short. Any calibration measured on a warmed-up robot does
not describe the robot at the start of a match.

## Correction to an earlier reading of this data

An earlier summary of this gate reported "the right wheel lands 85–90% every
time and never reaches commanded plateau speed" and treated a +14–21% L/R
imbalance as the stable finding. **That was wrong.** Those three runs all came
from one already-warm boot in which the left wheel had converged further than
the right; after a power cycle the two wheels are balanced (−0.5% / +1.1%) and
both start low. The previous chart is kept as
[velocity_profile_gate_prevboot_warm.png](velocity_profile_gate_prevboot_warm.png).
A residual right-wheel lag of a few percent does persist at convergence
(93.1% vs 96–98%), but it is a minor effect, not the headline.

The lesson for anyone using this gate: **record boot state and run index with
the result.** A single run in isolation does not characterize this robot.

## Running it

```bash
uv run python src/tests/bench/velocity_profile_gate.py --sim
uv run python src/tests/bench/velocity_profile_gate.py --port /dev/cu.usbmodem2121202   # confirm with `mbdeploy list`
uv run python src/tests/bench/velocity_profile_gate.py --port <RADIOBRIDGE> --profiles trapezoid
```

Exits nonzero on any wheel outside the PASS band (`--tolerance`, default ±5%).
That band is a **placeholder, not a measured bar.** On current firmware the
robot only clears it after several warm-up runs.

Sim passes both profiles (97–98%) and shows no cold-start deficit, so the
convergence behaviour above is the real robot, not the profile or the
measurement path.

## Note on a silent robot

A run against a powered-off robot produces `FAULTS OBSERVED: no telemetry
during the baseline window`, zero samples, and `nan` ratios — the gate refuses
to report a number rather than inventing one. The board still enumerates in
`mbdeploy list` when it is off, because that is the DAPLink interface chip, not
the application firmware; raw `PING` returning nothing is the tell.
