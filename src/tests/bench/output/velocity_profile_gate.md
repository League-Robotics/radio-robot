## Three consecutive runs

| run | trap L | trap R | sq L | sq R | R plateau tracking |
|---|---:|---:|---:|---:|---:|
| 1 (cold) | 94.0% | 77.3% | 90.9% | 78.4% | ~81% |
| 2 | 101.3% | 84.0% | 96.9% | 82.9% | ~81% |
| 3 | 102.7% | 89.8% | 98.4% | 85.1% | ~84% |

The left wheel converges toward 100% as the plant warms. **The right wheel
never reaches its commanded plateau speed** — ~84% of setpoint, stable across
runs and across *both* profiles — and its distance shortfall is essentially the
integral of that steady-state velocity deficit, not a start/stop management
problem. A proportional deficit at both 150 and 200 mm/s, on unloaded wheels,
with `wheel_deficit_right` never firing: the controller is neither correcting
it nor reporting that it cannot.

Sim passes both profiles (97–98%), so this is the robot, not the profile or the
measurement path.

## Running it

```bash
uv run python src/tests/bench/velocity_profile_gate.py --sim
uv run python src/tests/bench/velocity_profile_gate.py --port /dev/cu.usbmodem2121202   # confirm with `mbdeploy list`
uv run python src/tests/bench/velocity_profile_gate.py --port <RADIOBRIDGE> --profiles trapezoid
```

Exits nonzero on any wheel outside the PASS band (`--tolerance`, default ±5%).
That band is a **placeholder, not a measured bar** — set it from data once the
right wheel is fixed.
